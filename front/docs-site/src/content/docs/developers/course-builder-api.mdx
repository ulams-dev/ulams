The [AI Course Builder](/creators/course-builder/) is a plain REST API plus one Server-Sent Events (SSE) stream. The studio,
the [`ulams builder` commands](/developers/cli-builder/) and the MCP tools all use the same endpoints. Settings and limits
are in [Course Builder settings](/admin/course-builder/); the internals are in [LLM layer and Course Builder](/developers/llm-layer/).

## Conventions

- Base path `/api/admin/course-builder`, header `Authorization: Bearer <token>`. A [scoped token](/developers/scoped-tokens/)
  needs `builder:read` for GET and `builder:write` for everything else.
- The user needs the `course_builder_use` permission. Only the author of a session (and admins) can read it; only the author can change it.
- Responses are `{"success": true, "data": …, "message": "OK"}`; errors are `{"success": false, "message": "…"}`.
- Every endpoint below answers 503 with `"code": "ai_disabled"` while AI is off (`AI_DRIVER=disabled` or no API key); the [course-as-code endpoints](#course-as-code-endpoints-work-with-ai-off) do not.
- Ids of sessions, runs and versions are ULIDs; fragments are `frg_…`.

## Endpoints

| Method and path | Purpose |
|---|---|
| `GET sessions` | My sessions (latest 100), each with `costMicroUsd` |
| `POST sessions` `{title?}` | New session; 201 with the state snapshot, 429 after `COURSE_BUILDER_SESSIONS_PER_DAY` |
| `GET sessions/{session}` | State snapshot: `session`, `brief`, `briefRows`, `cost`, `sources`, `aiEnabled`, `budgetReached`, `activeRunId`, `canUndo`, `canRedo`, `links` |
| `DELETE sessions/{session}` | Cancel its active runs and delete the session; an applied course is kept |
| `POST sessions/{session}/sources` (multipart `file`) | Upload Markdown, PDF or DOCX; 202 with `source` and `runId` of the ingest run (the interview starts by itself after the first source); 422 with `reason` for a rejected file |
| `GET sessions/{session}/sources/{source}` | A source with its section tree (`fragments`) |
| `GET fragments/{fragment}` | One source passage, for a citation (`removed: true` when the source no longer has it and the archive does) |
| `GET sessions/{session}/brief`, `PUT sessions/{session}/brief` | Read or edit the Course Brief; the PUT returns `stale: true` when the outline no longer follows it (nothing is regenerated) |
| `POST sessions/{session}/runs` | Start a run from a chat message or a UI action (below); 202 with `runId` (null when the action finished inside the request), `accepted`, `message` |
| `GET runs/{run}` | Run status for pollers: `status` (`queued`, `running`, `succeeded`, `failed`, `cancelled`), `stage`, `needsAttention`, `steps[]`, `error` |
| `POST runs/{run}/cancel` | Cancel a queued or running run |
| `POST runs/{run}/steps/{step}/retry` | Retry one failed generation step; 409 for a step that did not fail |
| `GET sessions/{session}/events` | The SSE event stream (below) |
| `GET sessions/{session}/versions` | `currentVersionId`, `appliedVersionId` and the version history |
| `GET versions/{version}` | One version with its blueprint `document` and fragment labels |
| `GET versions/{version}/diff?against=` | Element-aware diff against another version (default: its parent) |
| `POST versions/{version}/approve` `{edits?}` | Approve a proposed outline, patch or content version; 409 when it is not waiting for a decision |
| `POST versions/{version}/reject` `{comment?}` | Reject a proposed outline or patch |
| `POST versions/{version}/restore` | Make an old version current as a new version |
| `POST sessions/{session}/undo`, `POST sessions/{session}/redo` | Move through the history; an applied course is re-applied |
| `POST sessions/{session}/apply` `{overwrite?}` | Create or update the course (unpublished); 202 with `runId`; 409 when there is no generated content |
| `POST sessions/{session}/publish` | Publish the applied course; 409 before the first apply |
| `GET sessions/{session}/usage` | AI calls by task and model: tokens, cost in micro-USD (1,000,000 = 1 USD), latency |

The session `status` moves through `draft`, `ingesting`, `interviewing`, `outlining`, `outline_review`, `generating`,
`apply_review`, `applying`, `applied` (or `failed`).

## Course-as-code endpoints (work with AI off)

Course-as-code moves a course between the academy and a repository without the AI pipeline. These endpoints live in their own
route group, `/api/admin/course-as-code`, and **do not answer 503 while AI is off**: the same token scopes apply (`builder:read` for
GET, `builder:write` for the rest) and so does the `course_builder_use` permission. The document they exchange is a
Blueprint v3 (`schemas/course-blueprint/v3.json` on this site); v1 and v2 documents are read as v3 (only `schemaVersion` changes, nothing is lost).

| Method and path | Purpose |
|---|---|
| `GET courses/{course}/blueprint` | The current version of a course as a v3 document: `courseId`, `sessionId`, `versionId`, `versionNumber`, `appliedVersionId`, `document`, and `drift` (elements an apply would change although an admin edited them) and `edits` (what an admin changed in the LMS after the last apply: `absorbable` elements, with their fields, that [`drift`](#reading-admin-edits-back-into-the-blueprint) can read back, and `unmapped` ones with the reason). 409 `NOT_ADOPTED` for a course that was not made with the builder, 409 `NO_BLUEPRINT` before any content exists |
| `POST sessions/{session}/imports` `{document, baseVersionId, message?}` | Store the document as a **proposed** version of kind `import` (origin `author`). 201 with `version`, `counts`, the element `changes`, `warnings`, `handEdited` (AI-written elements whose text you changed by hand) and `merged` (`null`, or what the server merged when your base was behind, see below). 200 with `unchanged: true` and no version when the document equals the current version (a `meta`-only change counts as unchanged). 422 `INVALID_BLUEPRINT` with `data.errors`, 422 `BASE_UNKNOWN`, 413 for a document over `COURSE_AS_CODE_MAX_DOCUMENT_MB` (8) |
| `POST sessions/{session}/drift` `{dryRun?}` | Read admin edits made in the LMS after the last apply back into a **proposed** version of kind `author` (see below). 201 with `version`, `counts`, `changes`, `absorbed[]` and `unmapped[]`; 200 with `unchanged: true` when there is nothing to absorb or with `dryRun`. 409 `NO_BLUEPRINT`, 409 `NOT_APPLIED`, 422 `INVALID_BLUEPRINT` |
| `GET versions/{version}` | One version with its blueprint `document` (the base a three-way merge needs) |
| `GET versions/{version}/diff?against=` | The element-aware diff, against the parent by default. It now includes self-checks and interactions |
| `POST versions/{version}/approve` | Approve a proposed `import` or `author` version (other kinds follow the builder's own flow). Needs a person, see below. 409 `NOT_PROPOSED`, 409 `STALE_PROPOSAL` when the course changed after the version was proposed |
| `POST sessions/{session}/apply` `{overwrite?}`, `POST sessions/{session}/publish` | The same as in the builder group, without the AI gate |

Errors carry a stable `code` next to `message`: `{"success": false, "message": "…", "code": "BASE_OUTDATED", "data": {…}}`.

**A push is always a proposal.** Nothing reaches learners until a version is approved *and* applied. Only the document
is trusted as data, never as instructions: it must pass the JSON Schema, the HTML, script-link and image checks and the citation
rules, and the server keeps the `sources` list it already has.

**A push that is behind the server is merged.** `baseVersionId` is the version your document started from. When it is not the current
version (the studio, a Living Course update or another push moved the course on), the server runs the same element-level three-way merge
as the CLI (`base`, your document as *ours*, the current version as *theirs*; one conflict per element, no field-level merge):

- **No overlap** (you and the server changed different elements): one **proposed** `import` is stored with the current version as its parent
  and your changes on top. `data.merged` says what came from where: `baseVersionId`, `currentVersionId`, `fromPush[]` and `fromServer[]`
  (element `id` and `kind`: `added`, `changed`, `removed` or `moved`) and `notes[]` (for example `ORDER_BOTH`: both sides reordered a list
  and the server's order was kept). `counts` and `changes` are against the current version. A document whose changes the server already
  has is `unchanged: true` (still with `merged`).
- **Overlap**: 409 `BASE_OUTDATED`, nothing is stored. `data` holds `currentVersionId`, `currentVersionNumber`, `remote` (what the server
  changed since your base) and `conflicts[]`: `elementId`, `type`, `label`, `kind` (`edit-edit`, `add-add`, `move-move`, `removed-ours` when
  you removed what the server changed, `removed-theirs` for the reverse, `slot`, `orphan`), `field` (the first conflicting field) and
  `fields[]` with `base`, `ours` (your pushed value) and `theirs` (the server's). Removing an element together with everything in it is
  one conflict when the other side changed anything inside; `held` counts those elements.

The merge is the same algorithm as `ulams course pull`; the two implementations share their test cases
(`api/packages/course-builder/tests/fixtures/merge/cases.json`).

**Who may approve.** A person logged in to the studio, or a `cli` token created by a person. An `agent` token or a request sent with
`X-Ulams-Client: mcp` never can (403 `APPROVAL_REQUIRES_HUMAN`): an agent proposes, the author approves. A `ci` token can approve only
when the tenant setting `course_as_code.ci_may_approve` is on (default off; the merged pull request then counts as the review).
Imports, approvals and who made them (user, token id and kind, `X-Ulams-Commit`, `X-Ulams-Change-Url`) are written to the session's
event log as `course_as_code.imported` (with `mergedWith` when the server merged), `course_as_code.drift_absorbed` and `course_as_code.approved`.
An `agent` token may call `drift` (it only proposes) and is refused when it approves what it absorbed.

### Reading admin edits back into the blueprint

An admin who edits an entity in the LMS after an apply changes what learners see, not the blueprint. `POST sessions/{session}/drift`
finds the elements whose LMS entity was changed after the last apply and whose mapped fields differ from what the apply wrote, and stores
a **proposed** `author` version with those values. It never touches the current version, the course or the entities. A field is read back
only where the blueprint still holds what was applied; otherwise it is `unmapped`, with a reason, and the blueprint value stays.

| Entity | Read back into | Not read back (listed as `unmapped`) |
|---|---|---|
| Course | `title`, `subtitle`, `description` | |
| Module (lesson entity) | `title`, `summary` | the generated final-test lesson |
| Lesson (topic) | `title`, `summary`, the Markdown, block by block (edited blocks become `origin: author`) | HTML from the visual editor, paragraphs added, removed or merged |
| Question | the stem, the option texts, the explanation | a changed correct answer, added or removed options, forms the GIFT reader does not know |
| Quiz topic, landing page | | everything (generated from the blueprint) |

`absorbed[]` entries carry `key` (`type:element id`, the same key as `drift[].element` of the export), `element`, `title` and `fields`.
Approving the version leaves the same entities "drifted" for an apply (the values are the same, the stored fingerprint is not): apply it with
`overwrite: true` only when every drifted element is in `absorbed[]` (`ulams course apply` does exactly that).

### Elements written by hand: `origin` and citations

Every element the AI creates or changes must cite at least one source passage. Text you write yourself has no source to cite, so
Blueprint v3 lets an element declare `origin: "author"` (blocks, lessons, questions, interactions and FAQ items; absent means `ai`):

- Only `origin: author` elements may have zero citations. Any citation that is present must still be a passage of the session's sources.
- Changing `ai` to `author` is possible only in an import, appears in the diff as a change of the field *Written by*, and is recorded in the
  `course_as_code.imported` event. The AI pipeline never sets `author`: when the AI edits an author block it becomes `ai` again and must cite.
- The import response and the publish check warn about author blocks without sources: Living Course cannot keep them up to date.

A lesson can also carry `key` (a slug for folder and file names), `meta` (ignored by apply and never diffed) and the reserved
`exercises` list. The content types `scorm`, `cmi5`, `video`, `file` and `embed` are part of the schema but are refused by this server
until their asset upload ships; the response says so.

```bash
# export, edit, import, review, approve, apply (a login or CLI token; an agent token stops at the import)
ulams course export 12 --out blueprint.json
$EDITOR blueprint.json
ulams course import --file blueprint.json --message "Fix the install step" --json
ulams course diff --version <version> && ulams course approve <version> && ulams course apply <session>
```

## Sending a message or an action

`POST sessions/{session}/runs` takes an AG-UI `RunAgentInput`. Typed text goes in `messages` (the last `user` message is used,
up to 4000 characters). With `forwardedProps.selection.elementId` the message starts a **patch** run on that element and the
result is a proposed version you approve or reject; without it, the text answers the open interview question or, during outline
review, requests changes to the outline.

```bash
curl -sS -X POST "$API/api/admin/course-builder/sessions/$S/runs" \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"messages":[{"role":"user","content":"Make this shorter"}],"forwardedProps":{"selection":{"elementId":"blk_x1"}}}'
```

A UI action goes in `forwardedProps.action = {name, surfaceId, context}`; the surface must be the open one the server issued
(an out-of-date card gets `accepted: false`). Actions: `answer {key, value}`, `decide_for_me {key?}`,
`approve_outline {versionId, edits}`, `reject_outline {versionId, comment}`, `approve_apply {versionId}`,
`approve_patch {versionId}`, `reject_patch {versionId}`, `retry_step {stepId}` and `retry` (repeats the interview or outline
step that failed). The `versions/{version}/approve|reject` endpoints are shortcuts that look up the surface for you, which is
what scripts should use.

## Reading the event stream with curl

`GET sessions/{session}/events` is `text/event-stream`. On connect you get `retry: 1000` and one
`STATE_SNAPSHOT` (no id, sent on every connect). Then every stored event after `Last-Event-ID` (or `?after=`), each as
`id: <n>` and `data: <json>`, then new events as they happen. The server closes the connection after
`COURSE_BUILDER_SSE_SECONDS` (25) and sends a `: ping` comment every 10 s, so a client reconnects with the last id.

```bash
# one connection, from the beginning
curl -sS -N -H "Authorization: Bearer $TOKEN" "$API/api/admin/course-builder/sessions/$S/events?after=0"

# resume after event 412
curl -sS -N -H "Authorization: Bearer $TOKEN" -H 'Last-Event-ID: 412' "$API/api/admin/course-builder/sessions/$S/events"
```

For a loop that survives the 25 s cap, use `ulams builder events <session> --follow --until-run <run>`
([NDJSON output](/developers/cli-builder/#events-as-ndjson)). Events are kept `COURSE_BUILDER_EVENTS_RETENTION_DAYS` (30) days.

### Event types

Every payload is `{"type": …, "timestamp": <ms>, …}`.

| `type` | Payload |
|---|---|
| `RUN_STARTED` | `threadId` (the session), `runId` |
| `RUN_FINISHED` | `threadId`, `runId`, optional `result` |
| `RUN_ERROR` | `message`, `code` (`error`, `cancelled`, or an AI failure reason such as `budget`), `runId` |
| `STEP_STARTED`, `STEP_FINISHED` | `stepName` (stage name, e.g. `ingest`, `apply`) |
| `TEXT_MESSAGE_START`, `TEXT_MESSAGE_CONTENT`, `TEXT_MESSAGE_END` | `messageId`; `role` (`assistant` or `user`) on start; `delta` on content |
| `STATE_DELTA` | `delta`: RFC 6902 patch on `/cost`, `/brief`, `/briefRows`, `/session`, `/sources`, `/budgetReached` |
| `ACTIVITY_SNAPSHOT` | `activityType: "a2ui-surface"`, `messageId` (the surface id), `content: {surfaceId, messages: [A2UI v0.9 …]}`, `replace: true`: the interview, outline, progress, patch and apply cards |
| `CUSTOM` | `name` and `value`: `applied {courseId, versionId, links}`, `published {courseId}`; with Living Course also `update_proposal`, `update_analysis`, `update_applied` |

`STATE_SNAPSHOT` (connect only) carries the snapshot described above. The cards are declarative A2UI components
([Generative UI](/developers/generative-ui/)); the CLI turns them into `data.pending` so an agent does not parse them.

## Cost limits and what happens at the limit

Every model call is checked before it is made, against three limits. The first that would be exceeded stops the call with a
`budget` failure:

| Limit | Setting (default) | At the limit |
|---|---|---|
| Tokens per session (cache reads count 10 %) | `COURSE_BUILDER_SESSION_TOKENS` (3,000,000) | "Budget reached: this course has used its AI token allowance." |
| Cost per session | `COURSE_BUILDER_SESSION_COST_USD` (5) | "Budget reached: this course has used $x of its $y AI budget." |
| Cost per tenant and month, all tasks | `AI_LIMIT_TENANT_MONTHLY_USD` (50; `0` turns the cap off) | "Budget reached: this academy has used its monthly AI allowance." |

The run fails with `RUN_ERROR` (`code: "budget"`), the session sets `budgetReached: true` (a `STATE_DELTA` on `/budgetReached`),
and everything already generated is kept. Raise the limit and retry the step or the run. Other limits answer before a run
starts: 429 for `COURSE_BUILDER_CONCURRENT_RUNS` (2 AI runs per author) and `COURSE_BUILDER_SESSIONS_PER_DAY` (10), 422 for a
source over `COURSE_BUILDER_SOURCE_TOKENS` (400,000), `COURSE_BUILDER_SOURCE_MB` (20) or `COURSE_BUILDER_PDF_PAGES` (300).
See [Course Builder settings](/admin/course-builder/) for the full table.

## Queues and timing

Runs execute in `RunJob` (one try, 1800 s timeout) on the `builder` queue; see
[Queues and streaming](/admin/course-builder/#queues-and-streaming). A poller should use `GET runs/{run}`, a UI should use the
stream.
