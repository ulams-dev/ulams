import { Aside, FileTree } from "@astrojs/starlight/components";

The reference frontend is three workspaces under `front/`, decided in
[ADR 0008](/decisions/0008-reference-frontend/) and planned in
[`docs/plans/phase-5-reference-frontend.md`](https://github.com/ulams-dev/ulams/blob/main/docs/plans/phase-5-reference-frontend.md):

| Workspace | Package | What it is |
|---|---|---|
| `front/web` | `@ulams/web` | Astro 5 app, server-rendered on every request (`output: "server"`, Node adapter), port 4321 |
| `front/sdk` | `@ulams/sdk` | Framework-free TypeScript API client on `fetch`; runs on Node and in the browser |
| `front/ui` | `@ulams/ui` | UI catalogue: Astro components and web components described by JSON Schemas, plus the renderer |

Pages are HTML rendered on the server with zero client JavaScript by default. Interactivity comes
from four small vanilla web components (`<ulams-quiz>`, `<ulams-h5p>`, `<ulams-video>`,
`<ulams-progress>`), bundled only on pages that use them. There is no React and no CSS-in-JS.
What learners see is described in [Learners](/learners/); this page covers the code.

### Why a new app

ADR 0008 chose a new Astro app over evolving the legacy React front. The audit behind it, in short:

| | Legacy React frontends (the upstream Wellms apps and `front/src`) | `front/web` |
|---|---|---|
| Rendering | Client-rendered single-page app: several hundred KB of JavaScript, nothing is painted before the settings and courses have loaded, so a course page has no server-rendered text for search engines | Server-rendered HTML on every request; zero client JavaScript by default (2.8 KB gzip on landing and course pages, 10 to 13 KB on a lesson) |
| Styling | CSS-in-JS in the upstream apps (the legacy front now refuses it in CI) | CSS custom properties, one stylesheet per theme (ADR 0004) |
| Tenant theming | Baked in at build time: a new look is a new build | Read per request from the tenant's settings (`theme.theme`, `theme.accent`, `theme.logo`) and rendered as CSS variables |
| Measured | Slow and janky on the demos (the reason for the rewrite) | LCP 55 to 126 ms cold on the demo academies, CLS at most 0.04, TTFB under 20 ms, against a budget of 1 s, 30 KB and 0.05 (production build, local API; `docs/plans/phase-5-reference-frontend.md`) |

The legacy front stays in the repository for the screens the new app does not have yet; the numbers are
measured again with `yarn workspace @ulams/web perf`.

### Theme, logo, manifest and structured data

The tenant's look is three public settings, all written from **Settings, Theme** in the admin (see
[Theme and logo](/operators/theme/)):

- `theme.theme`: one of the presets of the shared list, `front/ui/catalogue/themes.json` (generated from
  `front/ui/src/theme/presets.ts`; the API reads its copy `api/packages/settings/resources/themes.json`). A new
  preset is one CSS file in `front/ui/src/styles/themes/`, one entry in `presets.ts`, one stylesheet import in
  `layouts/Base.astro` and `yarn workspace @ulams/ui theme-manifest`; `yarn test` fails when the manifest or its API
  copy is stale.
- `theme.accent`: rendered by `lib/accent.ts` with at least 5:1 contrast on the preset background.
- `theme.logo` and `theme.logoAlt`: the middleware reads them from the cached public settings into
  `Astro.locals.tenantLogo`, and the catalogue's site header shows the logo (alt text: the one the admin wrote, else the
  company name) instead of the mark and the name. Only an `http(s)` address is accepted.

`/site.webmanifest` is a route: on a tenant host it answers with the company name, the `theme_color` of the preset and
the logo as the first icon (the platform icons follow, so the app stays installable); the platform host keeps the
product's manifest.

Every course page carries schema.org `Course` structured data (JSON-LD) built from what the API returned: the tenant as
`provider`, the course language as `inLanguage`, a `hasCourseInstance` that is online and self-paced (with the
workload when the course has a duration), and `offers` only when the course has a price above zero. A free course
has no offer. The author preview (`noindex`) carries none.

### Public product pages

On a platform host, `/`, `/pl/` and `/zh/` render the localized product Overview. The separate
Comparison page is available at `/comparison/`, `/pl/comparison/` and `/zh/comparison/`, and the
FAQ page, linked from the footer, at `/faq/`, `/pl/faq/` and `/zh/faq/`. Its questions live in
`src/data/faq.json` and `src/data/i18n/faq.<locale>.json`, grouped into topics that must keep the same
ids in every language. All page families use server rendered catalogue documents and the existing sourced comparison data. Public
product claims keep their actual roadmap status, including when a local preview setting hides those
labels elsewhere.

The course-generation pages (`/course-generation/`, `/pl/course-generation/`, `/zh/course-generation/`) show two real courses built from a source document, one page per case study (`microdosing-study`, `stablecoin-report`) with a frame slider of the Course Builder steps.

The blog is at `/blog/` (English) and `/pl/blog/` (Polish); there is no Chinese blog, so the Chinese header links to the
English one. Posts are files in `front/web/src/blog`, rendered with the `BlogIndex` and `BlogPost` catalogue
components; see [Writing docs](/contributing/writing-docs/#blog-posts) to add one.

`Base.astro` renders a page title, description, canonical URL, localized `hreflang` links including
`x-default`, Open Graph and X card tags, and escaped JSON-LD. Overview describes ulams as a software
application; Comparison is a collection page with breadcrumbs; FAQ emits one `FAQPage` with every
question, so its topic lists render with `jsonLd: false`. JSON-LD omits ratings, offers and
counts. `/robots.txt` points to `/sitemap.xml`; the sitemap lists the nine canonical product URLs, the
blog index and every blog post (English and Polish), each with its alternate languages. Both endpoints return 404 on tenant hosts.

### Markdown for agents

Every academy host serves `/llms.txt` ([llmstxt.org](https://llmstxt.org) format: the academy and its public
courses, each linked to its Markdown page) and `/llms/courses/<id>.md`, the page `/courses/<id>` shows
without signing in, as Markdown: title, lead, level, language, duration, teachers, tags, price, the
description and the syllabus with the format and length of every topic. Both come from the public API data
the HTML page uses (`src/lib/llms.ts`, pure functions with unit tests), are cached for 15 minutes and carry
nothing private: lesson content needs an enrolment and is not exposed. The platform host answers
`/llms.txt` with the product's own file; `/llms/courses/<id>.md` is 404 there.


The comparison matrix uses native tables with captions and scoped row and column headers. On narrow
screens, each table scrolls inside a keyboard-focusable region so the document itself does not scroll
horizontally. Overview links to Comparison from the shared header and footer.

### Configuration

All settings are runtime environment variables read when the server starts (`astro:env/server`,
never inlined into the build). Defaults are in `src/lib/config.ts` and `front/web/.env.example`:

| Variable | Default | Meaning |
|---|---|---|
| `ULAMS_TENANT_HOSTS` | `{slug}.app.localhost=>http://{slug}.localhost` | Host rules `<front host pattern>=><API URL template>`, comma separated, first match wins |
| `ULAMS_ADMIN_URL` | `http://{slug}.admin.localhost` | Tenant admin URL (demo badge) |
| `ULAMS_PLATFORM_HOSTS` | `app.localhost,localhost,127.0.0.1` | Hosts that serve the platform landing instead of a tenant |
| `ULAMS_DEFAULT_TENANT` | `coffee` | Tenant for hosts without a rule (for example a LAN IP); empty shows the tenant picker |
| `ULAMS_DEMO_TENANTS` | `gravity,poland,ulam,coffee,oncall,nightsky` | Demo tenants listed on the platform landing |
| `ULAMS_CACHE_TTL` | `45` | Seconds public API data stays fresh in the server cache (minimum 5) |
| `ULAMS_WARM_TENANTS` | `gravity,poland,ulam,coffee,oncall,nightsky` | Tenants whose public data is fetched at server start |
| `DEMO_STUDENT_EMAIL`, `DEMO_STUDENT_PASSWORD` | `student1@{slug}.ulams.app`, empty | Fallback login when a tenant has no demo mode; never sent to the browser |

### The platform landing content

Overview introduces the product, shows six live academy demos, explains the author-reviewed
source-to-course workflow, lists product principles and standards, shows a settled agent/API example,
and links to self-hosting. Comparison contains stakeholder and architecture summaries followed by the
sourced feature matrix. These public pages use the exported Stitch “Baskerville Editorial & Living
Knowledge” direction: warm paper surfaces, Baskerville headings, sans-serif interface text and restrained
terracotta actions. The agent/API example stays still instead of auto-typing. Public pages render roadmap
labels directly from source data; no display switch can promote planned work to shipped status.

### Landing languages

The platform landing is also served in Polish (`/pl/`) and Simplified Chinese (`/zh/`); `/` stays English. The routes are
Astro i18n routing (`i18n` in `astro.config.mjs`) and exist on a platform host only: a tenant host answers 404 there.
Each language is its own landing document (`src/docs/i18n/platform.pl.json`, `platform.zh.json`) with translated data files
(`src/data/i18n/`), and a unit test keeps the three documents parallel: same components, order, ids, links, icons and
statuses, untouched commands and code, and every product name still in the text. The fixed strings of the catalogue
components (badges, accessible names, buttons) follow the page language.

Each page sets `<html lang>`, a canonical URL and `hreflang` alternates (with `x-default` for English). The header has a
language switcher (EN, PL, 中文), separate from the six navigation links; it keeps the section you are reading. Chinese
uses the system font stack (PingFang SC, Hiragino Sans GB, Microsoft YaHei, Noto Sans SC) instead of a web font.
Overview and Comparison have separate localized routes; the language switcher keeps the visitor on the
same page in the selected language. See ADR 0096.

All variables of every app are in [Environment variables](/reference/environment-variables/). The
production image is described in [Container images](/developers/container-images/).

### Tenant resolution

`src/middleware.ts` runs on every request:

1. Reads the host from `X-Forwarded-Host`, then `Host`.
2. Refuses state-changing requests (`POST`, `PUT`, `PATCH`, `DELETE`) whose `Origin` (or
   `Sec-Fetch-Site`) is not this site, with 403. Astro's own origin check is off because it compares
   against the Node listen address behind the proxy.
3. Sets `locals.platform` for platform hosts; otherwise resolves `locals.tenant` with
   `tenantForHost()`, which uses `resolveTenant()` from `@ulams/sdk/tenant` and falls back to
   `ULAMS_DEFAULT_TENANT`.
4. On `/learn`, `/bff` and `/account` it ensures a session (below).
5. Adds `X-Content-Type-Options: nosniff`, `Referrer-Policy` and `Cache-Control: private, no-cache`
   on HTML.

The server then calls `tenant.apiUrl` directly (through Caddy in development). Public data
(settings, courses, course detail, tutors, events, products) is cached in memory per tenant,
stale-while-revalidate: fresh for `ULAMS_CACHE_TTL`, served stale for up to 30 minutes while it
refreshes, and warmed at start. Per-learner data (program, progress) is cached briefly per token and
dropped after progress writes. Measuring and tuning this is covered in
[Performance](/developers/performance/).

### Session and BFF

The API token lives only in the httpOnly, `SameSite=Lax` cookie `ulams_session`. How it gets there:

- `/login` posts the form to itself; the server calls `api.auth.login()` (one-month token) or, for
  "Continue as the demo student", the demo session, and sets the cookie.
- On session routes without a cookie, the middleware calls `demoStudentSession()`: demo login, else
  password login with the server-side fallback account. One demo token per tenant is cached and
  shared, because every demo visitor is the same seeded student.
- `/lti/launch` sets it after an LTI launch (below).

`/bff/[...path]` is the only way browser code reaches the API. It forwards a request to
`<tenant API><path>` with `Authorization: Bearer <cookie token>` only if it matches the allow-list in
`src/lib/bff.ts`:

```ts
// front/web/src/lib/bff.ts
export const BFF_RULES: BffRule[] = [
  { method: "GET", pattern: /^\/api\/profile\/me$/ },
  { method: "GET", pattern: /^\/api\/courses\/progress\/\d+$/ },
  { method: "PUT", pattern: /^\/api\/courses\/progress\/\d+\/ping$/ },
  { method: "PATCH", pattern: /^\/api\/courses\/progress\/\d+$/, writesProgress: true },
  { method: "POST", pattern: /^\/api\/courses\/progress\/\d+\/h5p$/, writesProgress: true },
  { method: "GET", pattern: /^\/api\/quiz-attempts$/ },
  // … quiz attempts and answers
];
```

Anything else gets 404, no cookie gets 401, an unreachable API 502. On a 401 from the API (tokens
are wiped by the hourly demo reset) the BFF logs the demo student in again once and retries. Rules
marked `writesProgress` drop the cached progress. Responses are `Cache-Control: no-store`.

To let an island call a new endpoint, add a rule: the BFF is deliberately not an open proxy. The
guide is [Adding a web page](/developers/adding-a-web-page/).

### H5P proxy

`/h5p/[...path]` proxies to `<tenant API>/h5p/<path>`, which Caddy sends to the H5P service. The
service only allows framing from the hosts in its `frame-ancestors` list; served through the front's
own origin the player page counts as `'self'`. The proxy passes bytes through unchanged, forwards
`Authorization` and a small set of response headers, rewrites `Location` to the front origin, and on
`embed/*` HTML pages narrows the embed's `allowedOrigins` to the front origin. No H5P code is bundled
into the front ([ADR 0003](/decisions/0003-h5p-as-isolated-gpl-service/)).

### LTI landing

`/lti/launch?code=…&course=…` is the target of `LTI_TOOL_LANDING_URL` when another LMS launches a
course. The server posts the one-time code to `POST /api/lti/tool/exchange`, stores the returned token
in the session cookie for 8 hours and redirects to `/learn/<course>` (303). A missing code gives 400,
an expired or invalid one 401 with a plain-text message. See
[Authentication](/developers/authentication/#lti-launches).

### Health check

`GET /healthz` answers `ok` with `Cache-Control: no-store`. It does not call the API, so it reports
that the Node server is up, not that the tenant API is reachable.

## @ulams/sdk

`front/sdk` exports `createClient` and helpers from `@ulams/sdk`, plus subpaths `@ulams/sdk/types`,
`@ulams/sdk/h5p` and `@ulams/sdk/tenant`. It has no runtime dependencies.

### Client

Every method returns the unwrapped `data` of the API's `{success, message, data}` envelope and throws
`ApiError` (with `status`, `path`, `body`; status 0 means the API was unreachable) otherwise.

```ts
import { ApiError, createClient } from "@ulams/sdk";

const api = createClient({
  baseUrl: "http://coffee.localhost", // or "/bff" in the browser behind the BFF
  token: process.env.TOKEN,           // omit in the browser when a server adds it
  timeoutMs: 15_000,                  // default
});

const { token, expires_at } = await api.auth.login("student1@coffee.ulams.app", "secret"); // remember_me on
const learner = api.withToken(token);

const courses = await api.courses.list({ per_page: 12 }); // { data, meta }
const program = await learner.courses.program(1);         // 403 without access
const progress = await learner.progress.course(1);

try {
  await learner.progress.ping(7);
} catch (e) {
  if (e instanceof ApiError && e.status === 401) {
    // log in again
  }
}
```

The client groups are `auth`, `settings`, `courses`, `progress`, `quiz`, `events`, `consultations`
and `products`; read `front/sdk/src/client.ts` for the methods. `raw()` returns the whole envelope (for pagination `meta`), `request()` any documented
path.

Request paths are typed as `ApiPath`, the keys of `paths` in `src/generated/openapi.ts`, generated
by `openapi-typescript` from the l5-swagger spec. The spec documents almost no response bodies, so
response types in `src/types.ts` are hand-written (marked TODO until the spec is complete). See
[API reference](/developers/api-reference/) and [OpenAPI and SDK](/developers/openapi-and-sdk/).

### Sessions

```ts
import { createClient, demoStudentSession } from "@ulams/sdk";

const session = await demoStudentSession(createClient({ baseUrl: "http://coffee.localhost" }), {
  fallback: { email: "student1@coffee.ulams.app", password: process.env.DEMO_STUDENT_PASSWORD! },
});
session.token;      // Passport token
session.expires_at; // ISO date
session.via;        // "demo" (POST /api/demo/login) or "password" (fallback)
```

### Tenant

```ts
import { resolveTenant } from "@ulams/sdk/tenant";

resolveTenant("coffee.app.localhost:4321");
// { slug: "coffee", apiUrl: "http://coffee.localhost", adminUrl: "http://coffee.admin.localhost" }

resolveTenant("academy.example.com", {
  pattern: "{slug}.example.com=>https://{slug}.api.example.com",
  adminUrlTemplate: "https://{slug}.admin.example.com",
});
```

The host rules are the same implementation the admin and the legacy front use
(`front/src/lib/tenant/resolveApiUrl.ts`, re-exported until the legacy front is removed).

### Topics

```ts
import { completionPercent, flattenTopics, resumeTopic, topicKind, topicNeighbours } from "@ulams/sdk";

topicKind("Ulams\\TopicTypes\\Models\\TopicContent\\Video"); // "video"
const next = resumeTopic(program, progress);                 // first unfinished topic
const percent = completionPercent(program, progress);        // 0–100
const { previous, next: following, index, total } = topicNeighbours(program, topicId);
```

`topicKind` maps topicable classes to `richtext`, `video`, `audio`, `image`, `pdf`, `oembed`, `h5p`,
`scorm`, `liascript`, `lti`, `cmi5`, `quiz`, `project` or `unknown`.

### H5P

```ts
import { h5pEmbedOrigin, h5pEmbedPlayUrl, isCompletingStatement, isH5PEmbedMessage } from "@ulams/sdk/h5p";

const src = h5pEmbedPlayUrl(tenant.apiUrl, 42, { language: "en", hideActions: true });
const origin = h5pEmbedOrigin(tenant.apiUrl);

window.addEventListener("message", (event) => {
  if (event.origin !== origin || !isH5PEmbedMessage(event.data)) return;
  if (event.data.type === "ulams-h5p:xapi" && isCompletingStatement(event.data.statement)) {
    // mark the topic complete
  }
});
```

The embed protocol (`ulams-h5p:ready`, `loaded`, `resize`, `xapi`, `saved`, `error` from the frame;
`token`, `style`, `save` to it) is documented in
[`api/h5p/README.md`](https://github.com/ulams-dev/ulams/blob/main/api/h5p/README.md).

## @ulams/ui

### Platform policy story

The Overview hero uses `PolicyStory.astro`: policy PDF and style-guide upload, cited source context, a four-question
course brief presented as an animated chat, departmental variants with distinct designs and example
tenant domains, training and PDF certificate, owner oversight, an approved
source update and renewal. Each chapter reveals its actions progressively. Play/pause controls
the scene animations and chapter playback. PDF text lines and citation fragments reveal individually
before the LLM reads them. Interface buttons use equal width and height, decorative icons and
subtle hover feedback, without redundant Available badges; keyboard navigation and reduced motion keep a static
view. Every chapter has three concise action bullets, including supported document formats and
images for course design, within a lighter layout without an enclosing card. EN/PL/ZH copy lives in the platform page documents and is checked against the Hero schema.

The story is an illustrative workflow. Departmental variants and an owner screen for compliance
reporting are **Coming**: the `compliance` package has required training, certificate expiry,
recertification, reports and a dashboard behind the API, but no admin screen, and an approved
source update does not yet invalidate certificates or reassign training. The platform page
shows webhooks as supported and tracks the Living Course and at-risk learner entries as built. Existing PDF extraction supplies cited fragments to the LLM; the
animation does not imply a vector retrieval service. Source updates retain owner approval.

The standards section supports an optional `Chips.research` note with a sourced summary, author,
PDF version date and verified links. The platform note references Mateusz Wojczal’s *ULAM Headless
Course Format* (PDF version 31 January 2022), with the PDF and its source repository. It is scholarly
context rather than an integration badge or a claim of peer review.

The `HeritageStory` section replaces the repetitive principles grid with the owner-selected Ulam
illustration, a sourced Scottish Book account, the product connection and a GitHub contribution link.
Historical context is separate from product inspiration. Asset provenance is recorded in
`front/web/public/landing/ulam/CREDITS.md`.

The catalogue is one registry, `front/ui/src/registry.ts`. Each entry has a description written for
a model, a category, whether it is interactive, whether it takes children, a JSON Schema for its
props (flat, explicit enums, defaults, safe-link format) and a plain-text fallback. The
[UI catalogue reference](/reference/ui-catalogue/) is generated from it.

## Comparison features by stakeholder

The Comparison page uses `FeatureIndex` with six `audiences`. Each of its fourteen `groups` has
an `audience` id. The catalogue restores 101 feature descriptions and 54 H5P content-type names
from the previous landing. Every product package is represented except the internal `core`
base classes. All feature prose remains in server-rendered HTML and ItemList JSON-LD. Native
`details` elements keep the long catalogue readable without JavaScript. EN/PL/ZH documents
share stakeholder ids, category ids, feature counts and documentation references.

The stakeholder categories are learners, authors/L&D, HR/managers/policy owners, sales/customer
teams, platform administrators, and IT/integrators/AI agents. Existing feature status labels
distinguish planned and preview capabilities. Overview remains a separate product narrative.

The shared header sets `aria-current="page"` on the matching Overview or Comparison link,
including mobile navigation and locale routes. The English root uses Astro's internal
`/platform` rewrite, which is normalised to the public `/` for matching.

For the existing Cloudflare Pages landing, `deploy/mydevil/cloudflare/landing-static.mjs`
exports all six Overview/Comparison URLs, client assets, robots.txt and the sitemap from
the production SSR build. Build with `ULAMS_IMAGE_SERVICE=noop` and production host settings.
Pass a new output directory; the exporter refuses to replace existing files.
