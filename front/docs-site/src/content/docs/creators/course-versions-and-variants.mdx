<Aside type="note" title="What is built and what is coming">
**Built:** course variants in the Course Builder (the interview question, one outline and one generation run
per audience from the same sources, each variant reviewed as a diff against the base, each approved variant
created as its own course and grouped with the base as a family); numbered course releases and a screen that compares
any two versions, a variant included; the **routing of learners between variants**: the learner's own choice, an assignment by an
administrator or a rule, the optional placement check, hints to switch, one entitlement for the whole family, progress carried over between variants and
mandatory training that accepts any variant; the **learner screens** for variants (the picker on the course page, the hint to switch and the optional placement check, see [Choosing your version](/learners/course-versions/)); a source update that reaches every variant as its own reviewable proposal (one analysis for all, shared elements take the base's patch at no cost); and certificates that name the variant. **Coming:** rebasing a variant on a newer base. Progress is tracked in the [roadmap](/roadmap/)
(Phase 3.1 and Phase 4.4); the design is in `docs/plans/course-versions-and-variants.md` and ADR 0192.
</Aside>

Two related features answer two questions authors ask about AI-built courses: **"what exactly changed
since last time?"** and **"why does everybody get the same course?"**

## What you can do today

These parts already work and the planned features build on them:

- **Releases** list every version of a course that learners got, newest first, with what started it, who approved it and
  what changed. Open **Versions** in the studio (`/studio/courses/<id>/versions`), or run `ulams course releases <id>`.
- **Compare** any two versions or releases on one screen. Open **Versions**, choose **Compare with previous** on a release, or tick
  any two releases and choose **Compare the two selected**. Turn on **Show all versions** to also pick proposals, rejected or replaced
  versions and the versions of a variant. The **Compare versions** screen (`/studio/courses/<id>/compare`) shows a summary, what learners would
  notice, the quiz answers that changed and the changed elements as a tree (added, removed, changed, moved and reordered, each marked by a
  word and a symbol), with the word-level text changes inline or side by side, the passages behind every citation that changed and the quiz
  impact of the element you select. **Compare the base course with a variant** opens the latest version of each. It works with the keyboard and a screen reader, in
  English, Polish and Chinese, and with AI switched off. The same comparison is available from the command line and for an AI agent:
  `ulams course compare <id> --from <a> --to <b>`.
- The [Course Builder](/creators/course-builder/) keeps every version of a course. **Version history**
  lists them, **Undo**, **Redo** and **Restore** move between them, and every AI change is shown as a diff
  you approve or reject.
- [Living Course](/creators/course-builder/#10-keep-the-course-in-sync-with-its-sources) proposes cited
  updates when a source changes, reviewed as one diff.
- Course-as-code (`ulams course diff`, `pull`, `push`) compares a course folder with the server, element by
  element ([worked example](/creators/git-sync-worked-example/)).
- The interview can ask for **extra versions of the course by level and role** (below).

What is still missing: the version list and the compare screen cover courses made with the Course Builder only; courses you built by hand get
them once they are adopted.

## Course versions with a visual diff

<Aside type="note" title="Partly built">
The version list, the comparison of any two versions and the compare screen are built (see above). The rest of this section describes the
planned behaviour so you can comment on it before it is built.
</Aside>

### The problem

A course changes for many reasons: you edit a lesson, the assistant rewrites a paragraph, a source update
is accepted, a colleague pushes from Git. Each change is reviewed on its own, but later nobody can answer
"what did learners see in March, and what is different now?" without reading both versions.

### Planned behaviour

- **A version for every change that reaches learners.** When an approved change is applied (your edit, a
  chat edit, an accepted Living Course update, a course-as-code push or an improvement from learner
  insights), the course gets a new numbered version. Each version records what triggered it, which source
  revisions it was written from, who approved it and when.
- **A version list per course** in the studio, newest first, with a one-line summary of each version
  ("3 lessons changed, 1 quiz answer changed, 5 citations updated").
- **Compare any two versions.** Pick two versions (not only neighbours) and the studio shows:
  - the course tree with modules, lessons and elements marked as added, removed, moved or changed;
  - word-level changes inside text, side by side or inline;
  - citations that were added, removed or now point to a newer revision of the source, with the passage
    text;
  - quiz changes: question, options, explanation and the correct answer, with a warning when a changed
    answer means learners will be asked to re-attempt (the existing progress rules decide that, past scores
    never change).
- **The same comparison everywhere.** The studio, the `ulams` CLI and the MCP server use one diff, so an
  agent and an author see the same changes.
- **Accessible by design.** Added and removed content is marked with text and icons as well as colour, and
  the comparison works with the keyboard and a screen reader.

## Course variants by level and role

Every learner used to get the same course: the expert waded through the basics and the beginner got lost in the
middle. Building separate courses by hand means separate sources, separate citations and separate updates that
drift apart. A **variant** is a branch of one course instead of a copy: it shares the sources and the citations of
the base course and becomes its own course in your academy once you approve it.

### Ask for variants in the interview

The interview has a card **Who is this course for?** with chips: **One course for everyone** (the default; nothing
extra is drafted and nothing extra costs), **Beginner version**, **Intermediate version** and **Expert version**.
Type roles in the box, separated by commas (for example `developer, support`), to add roles. Levels only give one
variant per level, roles only one per role, and both together give every level for every role. The card states what each
extra version costs about before you choose, and **Decide for me** keeps one course for everyone.

The course you approve first is the **base**, for the audience and level you answered in the interview. Each audience you add
is an extra variant, up to **6** per course (`COURSE_BUILDER_MAX_VARIANTS`, set by the operator; `0` removes the card). More are refused with the number
to remove.

### What happens next

1. **The base first.** You review the outline, approve it, review the lessons and apply the base course as usual. A variant is
   drafted from the approved base, so nothing is drafted before that.
2. **One outline per audience.** After the first apply the builder drafts a plan for each variant from the base course, the
   audience and an index of the source (not the whole source again): for every lesson it keeps, condenses, deepens or skips it, and it may
   add lessons the audience needs when the source supports them. You review each as the same outline comparison as for the base, against the
   base outline, with the reason for every change. **Request changes** with a comment drafts it again; approve it to start writing.
3. **Only what changed is written.** Kept lessons are copied with their text, quiz and citations and cost no model call. Condensed, deepened and added lessons are written
   again for the audience, and the final test is written again when any lesson changed. Every block still cites the source passages it rests on,
   passes the same grounding check and quiz support check as the base, and a lesson that fails can be retried on its own. Each model call is logged with the variant
   it belongs to, so cost per variant is visible, and the session budget stops all variants together.
4. **Review as a diff against the base.** Each finished variant shows how many lessons are kept, rewritten, added and skipped, and every changed
   text with word-level marks. Added and removed content is marked with text and icons, not only colour.
5. **Approve one by one.** Approving a variant creates it as its **own unpublished course** (its title carries the audience), through the same domain
   services as the base. A variant you have not approved is never created. Rejecting one creates nothing.
6. **A family in the catalogue.** The variant courses are grouped with the base course as a family and hidden from the public catalogue, so the family shows
   once, as the base course. Publishing the base course publishes the approved variants with it.

You can also add a variant later: the studio and the API accept a level and a role for a course that is already applied, and **Retire** removes
a variant from the cap (its course is kept).

### From the command line and the API

```
ulams course variants list <session> --json
ulams course variants add <session> --level expert --role developer --start --json
ulams course variants update <variant> --label "Expert, developer"
ulams course variants retire <variant> --yes
```

The endpoints are in the [Course Builder API](/developers/course-builder-api/) (`sessions/{session}/variants`, `variants/{variant}`). Review a variant with
`GET versions/{version}/diff?against=<base version>`: it is the same element diff the builder uses everywhere.

### Learners and variants

Learners are routed to a variant by their own choice, by an administrator or by a rule, never silently. The endpoints are in the
[Course variants API](/developers/course-variants-api/).

- **The picker.** The default course and every published variant of the family, each with its label, level, role and a line on who it is for, for anyone who can see the
  course page. The base course is one of the choices, usually labelled "Intermediate".
- **Choosing and switching.** A learner who has access to the course picks a variant and can switch later. Switching opens the other course for them, keeps the old
  course and its progress, and **carries completion over** for lessons that are the same in both variants. Quizzes are taken again in the new variant.
- **Assigned by your organisation.** An administrator can put learners or whole user groups in a variant, and **assignment rules** do the same by attribute
  (for example `department` equals `Sales`). A rule only routes learners who already have access and have no variant yet; it never enrols anyone and never overrides a learner's own choice or an
  administrator's assignment. A learner may change an assigned variant unless an administrator **locks** the course.
- **The placement check** (optional, off by default). A short set of questions made of the quiz questions the family already has, cited and tied to objectives, scored by code. It
  only advises: the result suggests a variant with its reason and the learner confirms it or picks another. Nothing is generated for it and nothing about the learner leaves the server.
- **A hint to switch.** If the variant looks too hard (struggling in the first two modules) or too easy (every quiz passed first time in the first two modules and under half the
  usual time), the learner sees a dismissible hint with the reasons. At most one per week, never an automatic switch, and dismissing it stops hints for that course. It needs Learner Insights.
- **One purchase, all variants.** One entitlement for any course of the family opens every variant: sell or assign the default course, and learners can use any variant. A
  refund or an expiry ends all of them, and the learner's progress is kept.
- **Mandatory training.** An obligation on the course is fulfilled by finishing any variant, unless an administrator **pins** one; then the learner is given the pinned variant and only it counts.

### What learners see

A learner of a course with variants finds **Choose your version** on the course page: every published variant with its level, role, duration and who it is for, the
version they are in, and **Switch to this version**. Switching keeps the old course and its progress and carries completed lessons over when they are the same in both
variants; quizzes are taken again. Where an administrator turned the placement check on, an enrolled learner can take it (advisory only: it suggests a variant and the learner
chooses), and a transparent hint can suggest an easier or more advanced variant, never switching on its own. A learner whose organisation assigned a variant sees
**Assigned by your organisation**, with the rule name, and cannot change it when the course is locked. The screens work with the keyboard and a screen reader, without JavaScript, in
English, Polish and Chinese: see [Choosing your version](/learners/course-versions/).

### Source updates and certificates

- **Living Course reaches every variant.** When a source changes, you get a proposal for the base course and one for each variant, grouped. A variant element that
  is the same as the base's is not analysed again: it takes the base's patch, so the same source change is analysed once and costs nothing extra for the variants
  that inherit it. Only elements a variant changed are analysed for it, with its audience in mind. Review each proposal as usual, accept a shared patch in all variants
  at once with **accept in group** (`POST .../items/{item}/accept-in-group`), and apply each on its own: applying a variant's proposal updates that variant's course, writes that variant's release and
  tells that variant's learners, and leaves the other courses alone.
- **Certificates name the variant.** Each variant course has its own certificate template (its title already carries the variant), a template can print the variant with
  `@VarCourseVariant`, and the public verification record of a certificate shows it.

### What is not built yet

- **A tabbed review of the group in the studio.** The API has it (`siblings`, `accept-in-group`); the studio's update screen shows one proposal at a time for now.
- **Rebasing a variant on a newer base**, and improvements from learner insights for a variant (they propose for the base course).
- **Chat edits on a variant.** The element chat edits the base course.

## Decisions behind it

The plan's open questions were settled with the recommended defaults. A variant is its own LMS course, so progress, completion, quizzes,
H5P and SCORM work exactly as in any course. The cap is 6 variants per course and the operator can change it. The base course is itself
an audience learners can pick. Mandatory training will accept any variant unless an administrator pins one, and a learner may change
a variant an administrator assigned unless the course locks it; both are built with the routing endpoints. The decision record is ADR 0192
and the full list is section 18 of the plan.
